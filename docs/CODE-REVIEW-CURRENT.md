## [P2] 获取 Key 期间的设置变化不会阻止旧页面信息被发送

位置：[history-workflow.js:25](../extension/history-workflow.js#L25)–33；相同模式也存在于 [organize-workflow.js:33](../extension/organize-workflow.js#L33)–37。

分类流程先读取页面、排除列表和记录状态，再异步获取 Key。等待 Key 时，另一面板可以完成网站排除、暂停记录或清空记录。Key 返回后，历史补分类只检查页面可见性和所选日期，没有刷新记录状态和分类上下文，随即使用旧的页面列表发出请求。普通工作区分类也直接使用获取 Key 前的快照。

定向复现：初始化一条 `private.example` 待整理历史记录，在 `getKey` 返回前将该域名加入排除列表并清空对应记录；请求回调仍收到这条记录。输出为 `recordsSent: 1`，随后工作流返回 `reason: changed`。复现使用假 Key 和本地模拟请求，没有实际发送浏览数据。

影响：虽然晚到结果不会覆盖已变化的记录，但已排除页面的标题和域名仍可能被发送到供应商。这里的请求是在设置变化之后才发出，不能仅用“已发出的请求无法撤回”解释。

建议：为两种分类流程建立共享的发送前检查，在最终发起请求的位置验证最新记录状态、排除列表、供应商、语言和上下文版本，并重新过滤正文与参考页面。将验证和请求启动置于可确定顺序的边界内，避免仅在响应后丢弃结果。补充“getKey 等待期间发生排除／暂停／清空，供应商请求次数必须为零”的回归测试。
