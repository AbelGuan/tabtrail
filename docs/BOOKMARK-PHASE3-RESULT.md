# Pickmark 2.0 第三阶段：书签 AI 分类

已接入现有插件。书签列表和网格的「AI 分类…」入口会先展示确认窗口；取消窗口不会发送请求。

## 使用与范围

- 使用当前书签筛选、搜索的全部结果，跨越分页；确认窗口列出总量、已分类/人工保护数量、本地规则命中数量、AI 待处理数量及供应商、模型。
- 确认前最多预览 50 条标题与域名；明确说明预览之外的待处理数量也包含在确认范围内。
- 先执行书签本地规则，再按每批最多 200 条调用 AI；已有分类和人工调整不会重新分配。
- 发送待分类书签的标题、域名、条目标识、分类名称和规则，不发送书签完整 URL、原文件夹路径或网页正文。使用用户配置的供应商和 Key，可能产生 API 费用。
- 每批完成后保存。取消、超时或后台终止后，已完成结果保留；再次点击「AI 分类…」重新确认，只处理剩余待分类书签。
- 等待期间若书签、分类、规则、供应商、模型、排除项或 Key 发生相关变化，过期结果不会覆盖新数据。
- 书签分类只写入独立的插件元数据，不移动或修改浏览器原书签，不修改标签页分类。导航页未加入。

## 回归结果

全部测试使用模拟数据、独立临时浏览器资料目录；AI 请求由本机假服务响应。没有访问个人浏览器资料、真实书签或邮箱，也没有调用收费 AI 服务。

| 检查 | 结果 |
| --- | --- |
| 静态检查与单元测试 | 101/101 通过 |
| 真实 MV3：45 秒慢响应 | 正常保存，服务工作线程未挂调试器 |
| 201 条分批，第二批处理中终止后台 | 保留前 200 条；迟到结果忽略；重新确认只发送剩余 1 条 |
| 真实 90 秒请求超时 | 待分类数据保留，重新确认后重试成功 |
| 真实界面确认、关闭窗口、中断重试 | 确认前零请求；关闭窗口零请求；中断后解除忙碌状态，重新确认可继续 |
| 历史补分类回归 | 确认、取消、本地规则、缺少 Key、已关闭页面、已有/人工分类保护、不自动打开标签、中英文及窄屏检查通过 |

## 性能复测

100、1000、10000 条模拟书签，列表、网格和三个面板均完成，无页面脚本错误。10000 条时每页仍只渲染 100 条：

- 列表显示约 96–131 毫秒，网格切换约 37–52 毫秒。
- 单面板回收后 JS 堆约 3.46–3.48 MB，三个面板合计约 10.46 MB。
- 反复切换十轮后 JS 堆约 3.64 MB，DOM 规模保持约 6400 个节点。

这些是本次机器上的模拟基准，不等于整个 Chrome 的内存。浏览器总进程 RSS 包括浏览器本身、共享内存等，不能作为插件独占内存。详见 [原始数据](offset-live/bookmark-phase3-stress.json)。

## 主要实现与可重复测试

- `extension/bookmark-ai.js`：确认范围快照、规则优先、分批请求、超时取消和保存前校验。
- `extension/bookmark-ai-workflow.js`：分批进度和重试流程。
- `extension/offset-ui.js`、`extension/offset-live.css`：入口、发送确认与进度反馈。
- `tests/bookmark-ai.test.js`：范围确认、保护已有数据、本地规则、并发人工修改、取消及重试。
- `scripts/bookmark-ai-lifecycle-check.mjs`：隔离 Chromium、模拟书签、回环 HTTPS 服务；仅临时复制的 manifest 预授予书签权限，生产脚本保持一致。

真实供应商质量与公网环境未在本轮调用验证；网络异常测试使用本机受控响应。
