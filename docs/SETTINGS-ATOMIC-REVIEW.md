## P2：API Key 在设置提交后另存，第二步失败会留下部分保存

位置：[dashboard.js:354](/Users/abelguan/Desktop/Tab/extension/dashboard.js:354)。

表单先调用 `send({type:'settings', ...})`，成功后才调用 `send({type:'key', ...})`。第二步发生容量错误或两步之间浏览器被终止时，第一步已经生效，后端一次提交的保护无法覆盖整个表单。

典型操作：用户同时新增排除域名并填写新 Key。设置保存成功已经按排除规则删除对应书签分类；随后 Key 保存失败，界面报告错误，但排除列表及书签分类已改变，Key 仍是原来的值。再次点击保存还可能被旧设置签名拒绝，需要重新打开设置。

模拟实际前端请求顺序，已确认：

- 旧排除列表 `[]` 变成 `['bookmark.test']`。
- 该域名书签原有的人工分类元数据已删除。
- Key 写入抛出 `QUOTA_BYTES`，旧模拟 Key 保留。
- 当前打开标签的人工分类仍完整；此次发现不涉及浏览器原书签被删除。

原复现入口：`node scripts/settings-form-review.mjs`。修复后已改为运行整体提交的正向回归，覆盖 Key、设置和关联数据。

建议：将表单中可选的新 Key 一并放进 `settings` 请求，在相同的版本校验和容量检查下，和配置、记录、缓存、书签元数据一起提交；空白 Key 继续表示保留原值。单独“忘记 Key”按钮仍可作为独立用户操作。随后补测表单级容量失败、两个请求原交界处的崩溃、多面板提交和各供应商 Key 隔离。
