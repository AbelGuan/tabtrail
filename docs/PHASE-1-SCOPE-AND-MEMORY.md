# 第一阶段：入口范围与内存说明

已完成：总菜单只保留全局设置入口及外观/语言控制；分类管理与规则从当前空间进入，并明确标注标签或书签。刷新进入当前页面工具栏，分别刷新标签数据或书签数据。标签工作区保留专属“重新分组”，书签只显示当前已实现的“应用书签规则”，没有伪装成书签 AI。标签整理在切换到书签或管理页面后停止后续批次；已经提交的标签任务不会被改成书签任务，已完成结果保留。

全局设置仍是共用配置，主动保存其中的供应商、排除网站等设置会按其现有全局含义生效；这与两套分类、规则操作相互独立不是同一件事。本轮没有实现第二阶段的书签管理能力对齐，也没有增加导航页或书签 AI。

验证：94 项单元测试及静态检查通过；总菜单/刷新/整理/规则/管理的空间隔离测试通过；界面多尺寸、分类排序、人工分类及历史补分类回归通过。仅使用模拟数据与临时浏览器，未访问真实书签或邮箱。

## 是否会让用户内存爆掉？

不能保证不会，但当前没有为每条书签后台打开网页的机制。展示标题、域名与分类，并不等于同时加载这些网站。悬停预览只读本地缓存，缺失时显示占位；截图需要用户显式保存当前可见页面。

已有的限制包括：缩略图最多 10 张、编码数据约 1.5 MB、7 天过期；浏览页面记录最多 5,000 条且保留最近 30 天。注意这些是存储/数据限制，不是运行内存上限；图片解码、DOM、JavaScript 对象、数据复制都会额外占用内存。

背景使用 MV3 Service Worker，Chrome 通常会在空闲约 30 秒后终止它，但事件或任务会延长存活。不能将这个机制等同于整个插件始终不占内存，打开的面板仍然占用页面进程资源。[Chrome 官方生命周期说明](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

现在最值得关注的风险：

- 书签树读取及列表/网格目前整批处理，未做大列表虚拟滚动。数千到数万书签会显著增加对象和 DOM 数量。
- 多开插件页面或侧边栏会产生多份界面状态，放大占用。
- 高频刷新会反复创建 DOM、过滤数组和事件回调，可能造成短时内存峰值和卡顿；是否泄漏需要长期测量，不能仅凭代码或功能测试下结论。
- 前端预览 Map 与持久化缓存不同，当前还需要检查长期访问时的淘汰策略，尤其是无缩略图的条目缓存。
- 用户批量恢复历史页面会实际打开网站，网站本身的内存可能远大于分类数据。分类整理不等于休眠、关闭或卸载网页。

Chrome 的 Memory Saver 会停用部分闲置标签以释放内存，重新访问时再加载。插件当前不是标签休眠工具，也不能替代这个机制。[Chrome 内存节省说明](https://support.google.com/chrome/answer/12929150?hl=en)

本轮做的是功能回归和代码层面的内存风险核对，没有完成压力测试，因此不提供“只占多少 MB”或“绝不会爆内存”的承诺。

建议下一轮单独做性能测试：使用模拟的 100/1,000/10,000 条书签，分别测列表、网格、搜索、多面板和连续切换；记录 JS 堆、DOM 数、浏览器进程内存、首屏耗时及垃圾回收后是否持续增长。根据结果优先加大列表虚拟滚动/分页、刷新合并和有界预览缓存，而非让插件自动关闭用户页面。
