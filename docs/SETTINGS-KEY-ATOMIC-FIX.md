# API Key 纳入设置整体提交

P2 已修复。设置表单现在只发送一个保存请求，API Key、设置、标签记录、停留记录、缓存和书签分类一起经过容量检查并写入。

## 行为

- 填写新 Key：去掉两端空白，更新所选供应商的 Key；其他供应商不变。
- Key 留空或只有空白：保留已有 Key，包括旧版本暂存于会话中的有效 Key；迁移也在同一次写入完成。
- 容量保护或浏览器配额拒绝：旧本地数据整体保留，不会先保存排除规则或删除分类。
- 设置版本号纳入并发校验：即使两个面板只修改 Key，也只接受同一版本的首次保存。“忘记 Key”后，旧设置面板也不能重新覆盖它。
- Key 通过独立消息字段传递，不放入普通配置、设置签名或预览演示的持久化配置中。
- 继续使用历史版本和书签修订号保护 AI 提交，保留人工分类及历史补分类流程。

## 验证

- 新增 Key 相关测试在修复前 3 项失败；修复后完整自动化测试 **131/131 通过**。
- `npm run check` 通过。
- 覆盖底层存储拒绝、Key 导致容量不足、空白保留、多供应商隔离、旧会话 Key、并发 Key 保存及忘记 Key 后的旧面板。
- `scripts/settings-key-crash-check.mjs`：真实临时 Chrome 中核对表单仅发送一次 `settings` 请求，没有后续独立 `key` 写入；空白保存仍保留原 Key。
- 两个真实扩展面板使用相同设置版本并发只改 Key：一个整体提交成功，另一个被拒绝。
- 设置提交前、提交后及恢复记录后强制退出测试浏览器进程组并重启：提交前完整旧数据保留；提交后新设置、Key 和关联数据共同保留。其他供应商 Key、当前人工分类及浏览器原书签保持正确。
- 清理及排除后的历史未被旧 AI 提交恢复，重启后新标签记录正常；原有书签和历史补分类回归继续通过。
