# 模拟书签压力测试与优化结果

已完成 100、1,000、10,000 条模拟书签的列表、网格和同时打开三个面板的测试。发现大列表一次性渲染造成显著内存与耗时增长，已改成每页最多渲染 100 条，并限制前端预览缓存。人工分类和历史补分类回归通过。

## 测量方式与边界

- 新建隔离 Chrome，1440×1000 视口；数据为固定结构的模拟书签，分成 20 个文件夹，无真实网址访问。
- 压测使用正式界面代码，但替换书签连接入口，直接提供模拟条目。因此主要衡量界面渲染，不包含真实 `chrome.bookmarks.getTree()` 的读取、传输及后台元数据处理成本。
- 每种规模使用独立浏览器，依次打开 1、2、3 个页面模拟多面板。不是直接测量三个原生侧边栏窗口。
- 通过 DevTools 在垃圾回收后读取 JS 堆、DOM 节点和监听器。JS 堆不包含全部图片解码、DOM、GPU 和浏览器内存，也不是整个插件的内存。
- RSS 是测试浏览器报告的进程 RSS 求和，包含浏览器基础开销，并可能重复计入共享内存，不能称为插件独占内存或系统物理内存消耗。
- 耗时包含自动化交互和等待元素出现的成本，属于本机单轮观测，未计算多轮均值或 P95，不应推广为所有设备的保证。
- 原始基线已完成九组规模/面板样本；为限制资源消耗，在 10,000 条基线的最后重复切换阶段停止。优化后所有规模均完成 10 轮列表/网格切换。

| 100 | 1,090.5 → 1,092.9 | 1,361.5 → 1,352.7 | 1,619.1 → 1,611.4 |

基线中三面板 RSS 反而低于两面板，反映采样时机、回收和进程共享的影响；不代表打开更多面板更省内存。不要把这组数当作峰值或线性增长公式。

优化后三面板下，每个 10,000 条书签列表的 JS 堆约 3.5 MiB，但仍有独立页面与浏览器开销，多开面板不会免费。

## 改动

1. **列表与网格统一分页。** 每页最多 100 条，提供上一页/下一页、当前位置与总数。搜索或分类筛选改变时回到第一页；结果减少时修正页码。
2. **全量语义保留。** 搜索仍查全部书签；“应用书签规则”仍处理当前筛选的全部结果，不限当前页。页面明确提示这一点。
3. **预览缓存有界。** 前端 Map 最多 20 个条目，包括无图片的缓存结果，防止长期悬停造成无限增长。磁盘缩略图原有的 10 张、约 1.5 MB、7 天限制继续保留。
4. **无后台网站加载。** 未增加自动打开书签、远程截图、书签 AI 或导航页功能。

## 稳定性与回归

优化后连续切换 10 轮，100/1,000/10,000 条的列表监听器均保持 805；最终节点约 6,355/6,399/6,434。10,000 条的 JS 堆从初始约 3.45 MiB 到约 3.63 MiB，没有观察到节点或监听器按切换次数累积。这个短时结果不能证明完全没有长期泄漏。

- 94 项单元测试与静态检查通过。
- 分页边界、第二页人工修改、列表/网格切换、搜索到末尾条目、空搜索结果通过。
- 在第一页以外人工修改的分类经全量规则整理后保留；末尾条目也正确参与整理。
- 前端预览缓存 100 次写入后只保留 20 项。
- 原有多尺寸界面、分类排序、书签规则回归通过。
- 历史补分类的确认/取消、无 Key、规则处理、已关闭页面、已有分类和人工调整保护通过。
- 临时配置中的真实 MV3 扩展回归通过，覆盖历史人工快照、书签分类持久化、原目录不变、标签关闭和侧边栏。

## 仍需注意

所有书签元数据仍会读入内存，本轮只是限制渲染；更大规模或大量深层文件夹还需测试。真实书签 API 读取耗时、复杂标题、真实截图解码、低内存设备和持续数小时运行不在本轮压力测试范围内。多个面板仍会各自保留数据。

结论：旧版确实存在大数据量下显著放大内存的风险，本轮已解决最主要的全量 DOM 渲染问题。现在 10,000 条模拟书签的显示成本接近 100 条，但不能承诺任何设备上都不会耗尽内存。
