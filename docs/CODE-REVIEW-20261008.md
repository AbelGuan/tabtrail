## 1. [P2] 页面记录缺少字节预算，达到条数上限前即可写入失败

位置：[core.js:60–62](/Users/abelguan/Desktop/Tab/extension/core.js:60)。相关写入位置：[background.js:40](/Users/abelguan/Desktop/Tab/extension/background.js:40)、[background.js:131](/Users/abelguan/Desktop/Tab/extension/background.js:131)。

`retainRecords()` 只按日期和 5,000 条上限裁剪。`collect()` 保存完整网页标题和 URL，分类成功后又将标题复制到 `aiTitle`。因此记录条数受限并不保证存储大小受限。活动片段虽然有独立的约 4 MB 预算，但页面记录没有对应预算。

复现：调用实际的 `collect()` 生成 5,000 条记录，每条标题为 1,100 个 ASCII 字符，然后模拟分类成功后的 `aiTitle`、`group` 和 `snapshotGroup` 字段。`retainRecords()` 仍保留全部 5,000 条；仅 records 的 JSON 就达到 **12,388,891 字节**，超过 Chrome local storage 的 **10,485,760 字节**配额，尚未计入 visits、配置和其他数据。项目没有声明 `unlimitedStorage`。配额及超限写入失败行为见 [Chrome 官方文档](https://developer.chrome.com/docs/extensions/reference/api/storage#property-local-QUOTA_BYTES)。

后果：正常积累的历史页面在长标题或长 URL 较多时，可以使同步或分类提交失败。`get` 会调用同步，而同步会再次尝试写入同样超限的记录，因此面板刷新也会反复报错，直至数据缩减。当前存储 mock 不实施配额，现有测试无法发现这个问题。

建议：为页面记录设置字节预算，并与活动片段、配置和其他持久化数据共享总预算；对单条超大记录限制存储字段长度。所有会放大记录的提交路径，包括写入 `aiTitle`，均应在提交前执行容量检查或裁剪。补充真实大小计算与拒绝超限写入的 mock 测试。

## 2. [P2] 每日回顾将午夜后的实际时长当作本地钟表时间，夏令时切换日归错小时

位置：[activity.js:34–36](/Users/abelguan/Desktop/Tab/extension/activity.js:34)。相关图表位置：[review.js:65](/Users/abelguan/Desktop/Tab/extension/review.js:65)。

`reviewData()` 使用 `midnight + from * 60000` 计算时间窗口，但界面将 `from` 解释为本地钟表时间。夏令时切换日有 23 或 25 小时，两者不再等价。泳道图重复使用同样的算法，因此只改筛选函数仍会留下图表错位。

使用 Node 子进程设置 `TZ=America/New_York`，直接调用实际 `reviewData()`，分别构造本地 10:00–10:01 的一分钟记录，得到：

| 日期 | 实际本地时间 | 归入的界面小时 | 正确的 10:00 时段结果 |
| --- | --- | --- | --- |
| 2026-03-08（进入夏令时） | 10:00–10:01 | 09:00 | 0 分钟 |
| 2026-11-01（退出夏令时） | 10:00–10:01 | 11:00 | 0 分钟 |

后果：用户选择一个小时或十五分钟时段时会看到其他时段的数据；秋季切换日的最后一个小时桶还会包含两个实际小时，而泳道图边界与筛选边界不一致。

建议：统一生成基于本地日期与时区的时间桶，让统计筛选、小时标签、十五分钟选项和泳道图使用同一组起止时间，并明确如何显示春季缺失的小时与秋季重复的小时。补充上述两个日期的回归测试，验证每条片段恰好归入正确时间桶，且图表范围与筛选范围一致。
