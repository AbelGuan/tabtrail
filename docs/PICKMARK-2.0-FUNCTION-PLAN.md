# Pickmark 2.0：双面板功能与导航入口方案

本轮仅核对项目源码与 Chrome 官方文档，未修改插件代码，未访问真实书签、邮箱或个人浏览器配置。以下明确区分已实现能力与建议功能；这是方案，不是完成功能的声明。

## 产品原则

标签页与书签是两个并列的数据空间，共享界面语言与操作方式。设置可以共用，操作对象必须明确。切换到书签后，整理、刷新、管理与规则都只作用于书签；同名分类不意味着两个空间自动关联。

标签回答“我正在处理什么”，书签回答“我想长期保存什么”。每日回顾、历史补分类不必硬搬到书签；原文件夹管理也不必硬搬到标签。

## 现状与目标对照

| 功能 | 标签页现状 | 书签现状 | 2.0 方案 |
|---|---|---|---|
| 列表、网格、搜索、分类筛选 | 已有 | 已有 | 共用组件；查询、筛选和视图偏好分别记忆，补齐持久化一致性 |
| 深浅色、跟随系统、语言 | 已有 | 共用 | 全局设置 |
| 紧凑/舒适行距、预览开关 | 已有 | 共用 | 全局展示设置 |
| 人工分类 | 已有，并保护人工调整 | 已有独立分类元数据 | 同一交互；两边分别保存，自动整理不能覆盖 |
| 分类新建、改名 | 已有，支持点击名称编辑 | 已有基础新建/重命名表单 | 书签补齐同款直接编辑与取消、错误提示 |
| 分类图标、排序、合并、删除 | 已有完整入口 | 尚未齐备；后台有删除到待整理能力，但界面未开放完整操作 | 共用管理界面，书签补齐存储、并发校验、操作确认和回归测试 |
| 关键词规则 | 新增、编辑、删除、排序 | 基础新增/删除；同关键词可更新，但没有完整编辑入口 | 共用规则页与优先级操作，默认分开保存 |
| 规则备份与导入 | 已有 | 未接入 | 统一文件格式，明确来源与目标空间；导入前预览，不覆盖已有优先级 |
| 整理待分类 | 本地规则＋AI；工作区可见时可自动处理 | 手动触发本地规则，保护已有与人工分类 | 书签补齐 AI；初期由用户主动发起，并显示范围 |
| AI 供应商、Key、模型 | 已有 | 尚未用于书签分类 | 共用配置；允许处理标签/书签的选择分别保存 |
| AI 分类偏好、规则建议 | 已有 | 未接入 | 两边使用相同流程，偏好默认分别保存；后续可明确选择复制 |
| 强制重新分组 | 已有确认流程，可能改变人工分类 | 没有等价流程；旧总菜单仍指向标签逻辑 | 改成当前空间的高级操作，默认排除人工分类，覆盖需单独勾选并确认 |
| 刷新 | 刷新标签数据 | 已有读取与书签事件更新；总菜单“同步标签”未适配 | 当前页面提供“刷新标签页/刷新书签”；不称跨设备同步 |
| 悬停预览 | 本地缩略图缓存，缺失时占位 | 同一缓存机制 | 共用；当前不是自动获取任意网站截图，不后台打开书签 |
| 每日回顾、时间与轨迹 | 已有 | 不适用 | 标签专属 |
| 继续浏览、恢复清单、历史补分类 | 已有 | 不适用 | 标签专属，保持已有分类和人工调整保护 |
| 浏览器原书签文件夹 | 不适用 | 授权后读取，插件分类不移动原目录 | 书签专属；与“智能分类”明确分开 |
| 打开页面 | 跳回已有标签或恢复页面 | 打开书签目标 | 相同入口，不同行为；不自动批量打开 |
| 跨设备同步 | 没有插件自身同步方案 | 原书签是否同步由浏览器决定，插件分类是本地数据 | 不列为已支持；后续独立设计 |
| 新标签页导航入口 | 未声明新标签页覆盖 | 同左 | 单独评估并开发，见后文 |

目前标签分类与书签分类使用独立存储。书签后端也还缺少与标签侧对齐的操作版本检查和完整参数校验；补齐管理能力时应同步解决，不能只复制按钮。

## 统一入口

### 全局顶栏

左侧保留「标签页｜书签」。右侧搜索默认检索当前空间，并显示“搜索标签页”或“搜索书签”。全库联合搜索可留到后续，届时结果必须标注来源。

右上角总菜单仅包含全局内容：

- 设置与隐私：外观、语言、AI 连接、分空间授权与数据管理。
- 使用帮助与版本信息。
- 导航入口设置：在相关能力真正上线后出现。

避免把管理、规则、刷新重复放进总菜单。外观和语言可保留快捷控制，但与设置页共用同一状态。

### 当前空间左侧

| 标签页 | 书签 |
|---|---|
| 工作区、每日回顾、继续浏览 | 原文件夹、智能分类 |
| 当前分类列表 | 当前文件夹或智能分类列表 |
| 底部：分类管理、分类规则、设置 | 底部：分类管理、分类规则、设置 |

管理页标题显式显示“标签分类管理”或“书签分类管理”；规则页同理。设置始终是全局设置，不随空间切换变成另一套账户配置。

“原文件夹”视图中的分类管理仍然管理插件的智能分类，不改浏览器目录。入口旁说明这一点，页面切换后明确进入“书签智能分类”。不提供一个名字含混的“管理文件夹”按钮。

### 当前页面工具栏

主操作为“整理待分类”，次操作为“刷新”，右侧保留列表/网格与行距。进度显示实际范围，例如“书签 · 设计分类 · 18 条待整理”。高级菜单放“重新分类…”。

在原文件夹视图点击整理，含义是“为此范围建立智能分类”，结果不会重排原目录。继续浏览页保留专用“历史补分类”，不换成含糊的统一按钮。

## 两边共用的行为约定

1. **先明确范围再执行。** 默认当前空间、当前筛选及搜索范围；范围在确认页和进度中保持一致，切换页面不暗中改变任务对象。
2. **默认增量补齐。** 整理只处理待分类项目，保留已有分类、人工调整与规则结果。重新分类是明确的高级动作。
3. **规则默认独立。** 标签与书签允许同关键词归入不同分类。第一阶段提供“复制到另一空间”，不引入隐式共享规则；后续共享规则需要再定义冲突优先级。
4. **管理对象是分类元数据。** 删除分类不删除页面、书签或浏览记录。合并迁移归属及规则；目标分类图标和顺序保持，源分类移除。书签原目录保持不变。
5. **隐私边界明确。** 供应商和 Key 共用不等于允许发送书签。书签本地读取授权、书签 AI 发送选择要分开；可发送字段应说明为标题、域名和必要分类上下文，不能顺手发送目录路径或完整网址。
6. **数据清理分空间。** “清空浏览记录”“清空书签智能分类”“清除预览缓存”分开，不能出现不说明范围的“清空全部”。当前共享排除站点设置也应明确作用范围；迁移时不得放宽用户已有排除设置。
7. **任务可靠性对齐。** 书签 AI 必须补齐超时、取消、后台终止、断点重试、去重、数据变化后拒绝旧结果和费用范围提示，达到历史补分类同等保护水平。

## 导航页：可行，但要区分三种入口

适合作为新标签页：书签提供长期入口，标签提供当前任务，继续浏览提供返回路径。建议先复用现有双面板，不另造一个堆天气、资讯和时钟的首页。可选择默认打开“书签”“标签页”或“上次使用的面板”；新用户推荐书签，但没有授权时展示连接入口，不提前读取。

| 用户说的导航页 | 实际触发方式 | 建议 |
|---|---|---|
| 新标签页 | 点击＋或 Cmd/Ctrl+T | 最适合 Pickmark 的入口 |
| 主页 | 点击浏览器主页按钮 | 可提供说明，非首期重点 |
| 启动页 | 启动浏览器时打开 | 尊重用户恢复上次会话的习惯，首期不主动修改 |

Chrome 支持通过扩展清单的 `chrome_url_overrides.newtab` 替换新标签页；无痕窗口不支持这项覆盖。当前插件没有声明它，所以现在尚不会成为新标签页。[Chrome 官方说明](https://developer.chrome.com/docs/extensions/develop/ui/override-chrome-pages)

安装后可以利用 `runtime.onInstalled` 的首次安装事件展示一次欢迎说明，避免每次更新都再次打扰用户。[Chrome 安装事件](https://developer.chrome.com/docs/extensions/reference/api/runtime#event-onInstalled)

**但“安装后询问是否开启”与“可随时自由开关新标签页覆盖”不是同一回事。** 新标签页覆盖由安装包清单声明，不是 `permissions.request` 那样的运行时可选权限。根据这一机制，不能承诺在普通版本里点一下设置就新增或移除该声明。也不建议靠监听新建标签并重定向来伪装这一能力。

建议在发布前选择以下一种真实可行的产品形态：

- **推荐先保持当前主插件不接管新标签页。** 首次欢迎页可介绍导航用途，提供“打开导航面板”“暂不设置”。若必须严格做到用户之后自主加装，评估一个可选的新标签页入口扩展；它负责覆盖并连接主插件。需要验证两扩展通信、数据授权、安装依赖和下架/卸载时的处理，不属于现成的一键功能。
- **若导航是 2.0 的核心定位，则发布明确的新标签页版本。** 在安装说明中提前披露覆盖行为，安装后欢迎页用于选择默认面板和授权。不能在已经声明接管的版本中，把“暂不设置”包装成没有接管；恢复方式必须遵循浏览器实际控制机制，并实测与其他新标签页扩展的冲突。

浏览器主页和启动页属于另一套设置覆盖机制，官方文档列出了平台、域名验证及额外确认方面的要求，因此不与新标签页混用，也不顺带修改默认搜索引擎。[Chrome 设置覆盖说明](https://developer.chrome.com/docs/extensions/reference/manifest/chrome-settings-override)

导航模式还需增加两项验收：新标签页不计入自己的浏览统计，不因每次打开导航页重复启动付费 AI 请求；首屏先读取本地展示数据，整理在明确的任务策略下运行。新标签页初始焦点通常在地址栏，页面不能抢焦点。[Chrome 新标签页设计建议](https://developer.chrome.com/docs/extensions/develop/ui/override-chrome-pages)

## 推荐实施顺序

| 顺序 | 范围 | 完成标准 |
|---|---|---|
| 1 | 修正总菜单与操作范围 | 书签模式不出现“同步标签”，也不会误执行标签重新分组；全局与当前空间入口清楚 |
| 2 | 对齐管理、规则与状态 | 书签拥有名称编辑、图标、排序、合并删除、规则编辑排序和备份；未授权、空数据、错误状态一致 |
| 3 | 补齐书签 AI | 独立同意、范围确认、增量保护、后台终止与重试全部经过隔离测试 |
| 4 | 新标签页导航 | 先确定发行与启用机制，再做欢迎页、默认面板、首屏性能和入口冲突测试 |

每一阶段都回归标签工作区、人工调整、历史补分类、规则迁移及浏览记录恢复。开发使用模拟标签、测试书签和临时浏览器配置，无需读取你的真实书签或邮箱。

本方案的优先建议：先让双面板真正对等，再将稳定的数据和操作体验作为导航页入口；不要先给未完成的书签能力套上相同菜单。
